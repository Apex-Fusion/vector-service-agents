A checkout that runs with `core.autocrlf=true` has CRLF working files, while the blobs are LF and so is every checkout of this repository (`.gitattributes` says `eol=lf`). A `cp` of such a working file records a sha256 that no checkout of this repository reproduces. The mcp-server checkout of the first copies (at `651ae93`) ran with `core.autocrlf=true`, and each of its working files was checked to equal its blob once CR is stripped. The agents-marketplace clone runs with `core.autocrlf=true` too, and its working tree is a stale branch while the copies come from `origin/main`: the two fleet files were taken from the blobs and no working file of that clone was read.

## Why vendored

Apart from the signer, the mcp-server packages are not published to a registry. The signer is published on npm as `@apexfusion/vector-mcp-signer` (version 2.0.0, 2026-10-16), but as a command, with four files: `build/index.js`, `README.md`, `LICENSE.md` and `package.json`. `src/sign.ts` is not among them. The Document Pipeline agent (deployed since 2026-10-16) posts escrows, signs and submits transactions, reads escrow lineage and verifies receipts. It builds, reads and verifies with the same code the hosted keyless MCP server uses: the same datum codecs, the same builders, the same lineage resolver and the same receipt verifier. It signs with `sign.ts` of the member's local signer package (`packages/signer`). The hosted server never signs: it returns unsigned transactions, and the member's local signer signs them.

The datum codecs and the identity codecs are not copied a second time. `@vsa/vector-read` carries `marketplace-datum.ts` (its `src/datum.ts`, above the marker) and `identity-codec.ts` (its `src/identity-codec.ts`), both at `94bd293`, and the copies here import them from there: the datum codecs from `@vsa/vector-read`, the identity codecs from the subpath `@vsa/vector-read/identity-codec`. Drift is caught twice: by the tests of `packages/vector-read` (`test/datum.test.ts`, the golden datum tests of the source, and `test/identity-codec.test.ts`, the source's tests of the identity codecs on the Aiken CBOR fixtures) and by the sha256 column below, which `test/vendored.test.ts` checks in both directions: every row names a file whose sha256 matches, and every file under `src/vendored/` and `test/fixtures/` has a row.

Since `ef374f8` the copies serve both layouts of the drain (did:vector Part 2, section 6.5): the legacy escrow and advert, and the escrow and advert of the identity marketplace, whose scripts take the parameters of the identity registry deployment. The copies read an identity-marketplace advert or escrow only with that deployment, an `IdentityDeployment` (`identityDeploymentFrom` of `identity-deployment.ts` reads it from the two deployment values). Without it they serve legacy adverts and escrows only: a Post to an identity-marketplace advert and a read of an identity-marketplace escrow are refused with a text that names the two settings (`NOT_CONFIGURED`).

The fleet is not published to a registry either. The Pipeline commits to the request of a fleet job and to its answer with the fleet's own Responses code, `responses.ts`: the normalisation of the request, the request commitment, the result commitment and the normalisation of the output. A copy of that code is what makes the hash computed here the hash a fleet supplier computes; a re-implementation could drift with no test noticing. `fleet/types.ts` is the one type that file imports, `ChatMessage`, with the one type `ChatMessage` refers to, `ToolCall` (see Deviation: three excerpts). The repository Apex-Fusion/agents-marketplace carries no LICENSE file at its root (none anywhere in its tree at `e847a55`; at `4c95c3f` the only LICENSE file in its tree is `identity-gateway/LICENSE`, in a folder that is not copied here). A build-time ruling: this is code of the same organisation's public repository, copied unchanged but for one import line, and the missing licence is flagged to the operator as a licence-hygiene item.

## Signature rules and node answers

PR #46 of the mcp-server changes two rules. `ebce68a` is its merge into main. Four copies follow it, and `ed25519-rules.ts` is new.

**A node answer with no list is an error.** An answer of Ogmios to a read of outputs or to the evaluation of a transaction can hold no list: `"result": null`, no `result`, or a `result` that is not an array. The source read such an answer as an empty list, so a check said "not found" where "cannot read" is right. Now the answer is an error with the text `Ogmios request failed (<method>): the node gave no list`. The error names the method and nothing else. The log line for the operator names the node and the kind of the answer, and never its content. The private method `rpcList` of `OgmiosProvider` makes the check. Four readers call it: `getUtxos` (`getUtxosWithUnit` reads through it), `getUtxosByOutRef`, `evaluateTx` and `evaluateTransaction`. An empty array is a list and stays empty. The readers of other answers (the tip, the start time, the block height, the protocol parameters and the reward account) are as before. `nodeFailure` of `marketplace-lineage.ts` passes the new text on, so the read of an escrow fails with `... from the node: Ogmios request failed (queryLedgerState/utxo): the node gave no list`.

**A key of small order never verifies.** `ed25519-rules.ts` holds `signatureVerifies`. It refuses a public key of a small order, a signature whose R has a small order, and a key or a signature of the wrong size. Then CML checks the encoding of R, that S is below the group order, and the equation. The check of CML alone takes a forged signature for a key of a small order: R = the identity point and S = 0 verifies over some messages, and over every message when the key is the identity point. `envelopeVerifies` of `attestation-build.ts` and the receipt check of `marketplace-verify.ts` call `signatureVerifies`. In this package, `checkAttestation` calls the first, and `verifyFleetReceipt` calls the second. A normal key and signature give the same result as before. A key or a signature that cannot be read does not verify, and nothing throws. The source moved these rules out of its co-sign code of delegations (`delegation-cosign.ts`), which is not copied. The new file decodes no CBOR (it reads raw key and signature bytes), so `test/cbor-guard-sites.test.ts` does not name it.

The read and check code of attestations, delegations and vaults, and the builders of the four Module-1 transactions (a document, a claim, a challenge and the withdrawal of a claim), are copies of Apex-Fusion/mcp-server at `2d95483`, but for `attestation-build.ts` (see Signature rules and node answers) and for `delegation-build.ts`, `vault-build.ts` and `vault-read.ts` (see Builder refusals, the vault Pay and the change address), which are at `ebce68a`. **Where they sit.** The copies sit in `src/vendored/mcp/`, next to the copies that they import, and not in `@vsa/vector-read`. The read code needs a node `Provider`, the identity deployment, `identity-chain.ts` and `marketplace-indexer.ts`, and all three are copies of this package.
