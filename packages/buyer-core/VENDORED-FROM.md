# Vendored from Apex-Fusion/mcp-server and Apex-Fusion/agents-marketplace

The files under `src/vendored/mcp/`, `src/vendored/mcp-shared/` and `src/vendored/signer/` and the six files under `test/fixtures/` are copies of files of Apex-Fusion/mcp-server at commit `94bd293` (`94bd293403039e2c9762e0c86a87892467cbc9c6`, committed on 2026-11-03 at 01:15:28 +0100). It is not a merge commit: it is the head of the branch `feat/identity-registry`, which is not merged into main. After the pin before, that branch was rebased onto `4f01518`, the commit of PR #25 on main (2026-10-23). So the pin before is not an ancestor of `94bd293`. The copies before it were at `f456194` (`f45619410aaeafeb287b36958ef251c38cf8186d`, committed on 2026-11-02 at 20:35:53 +0100) and before that at `ef374f8` (`ef374f878f7ac8f44eb32c68b0be12a1d2f63de3`, committed on 2026-11-02 at 19:18:59 +0100), two heads of the same branch before the rebase, and before that at `651ae93`, the merge of PR #24 into main on 2026-10-14. The two files under `src/vendored/fleet/` are copies of files of Apex-Fusion/agents-marketplace at commit `e847a55` (`e847a553146516e574f3cadb6688d74dd4cf2b7b`, committed on 2026-10-13, the `origin/main` of the clone it was taken from on 2026-10-15).

Each copy was taken from the blob at its commit, `git -C <checkout> cat-file blob <commit>:<path>`, never from a working file. A checkout that runs with `core.autocrlf=true` has CRLF working files, while the blobs are LF and so is every checkout of this repository (`.gitattributes` says `eol=lf`). A `cp` of such a working file records a sha256 that no checkout of this repository reproduces. The mcp-server checkout of the first copies (at `651ae93`) ran with `core.autocrlf=true`, and each of its working files was checked to equal its blob once CR is stripped. The re-vendors at `ef374f8`, `f456194` and `94bd293` took every copy from its blob too. The agents-marketplace clone runs with `core.autocrlf=true` too, and its working tree is a stale branch while the copies come from `origin/main`: the two fleet files were taken from the blobs and no working file of that clone was read.

## Why vendored

Apart from the signer, the mcp-server packages are not published to a registry. The signer is published on npm as `@apexfusion/vector-mcp-signer` (version 2.0.0, 2026-10-16), but as a command, with four files: `build/index.js`, `README.md`, `LICENSE.md` and `package.json`. `src/sign.ts` is not among them. The Document Pipeline agent (deployed since 2026-10-16) posts escrows, signs and submits transactions, reads escrow lineage and verifies receipts. It builds, reads and verifies with the same code the hosted keyless MCP server uses: the same datum codecs, the same builders, the same lineage resolver and the same receipt verifier. It signs with `sign.ts` of the member's local signer package (`packages/signer`). The hosted server never signs: it returns unsigned transactions, and the member's local signer signs them.

The datum codecs and the identity codecs are not copied a second time. `@vsa/vector-read` carries `marketplace-datum.ts` (its `src/datum.ts`, above the marker) and `identity-codec.ts` (its `src/identity-codec.ts`), both at `94bd293`, and the copies here import them from there: the datum codecs from `@vsa/vector-read`, the identity codecs from the subpath `@vsa/vector-read/identity-codec`. Drift is caught twice: by the tests of `packages/vector-read` (`test/datum.test.ts`, the golden datum tests of the source, and `test/identity-codec.test.ts`, the source's tests of the identity codecs on the Aiken CBOR fixtures) and by the sha256 column below, which `test/vendored.test.ts` checks in both directions: every row names a file whose sha256 matches, and every file under `src/vendored/` and `test/fixtures/` has a row.

Since `ef374f8` the copies serve both layouts of the drain (did:vector Part 2, section 6.5): the legacy escrow and advert, and the escrow and advert of the identity marketplace, whose scripts take the parameters of the identity registry deployment. The copies read an identity-marketplace advert or escrow only with that deployment, an `IdentityDeployment` (`identityDeploymentFrom` of `identity-deployment.ts` reads it from the two deployment values). Without it they serve legacy adverts and escrows only: a Post to an identity-marketplace advert and a read of an identity-marketplace escrow are refused with a text that names the two settings (`NOT_CONFIGURED`).

The fleet is not published to a registry either. The Pipeline commits to the request of a fleet job and to its answer with the fleet's own Responses code, `responses.ts`: the normalisation of the request, the request commitment, the result commitment and the normalisation of the output. A copy of that code is what makes the hash computed here the hash a fleet supplier computes; a re-implementation could drift with no test noticing. `fleet/types.ts` is the one type that file imports, `ChatMessage`, with the one type `ChatMessage` refers to, `ToolCall` (see Deviation: three excerpts). The repository Apex-Fusion/agents-marketplace carries no LICENSE file (none at the root or anywhere else in its tree at `e847a55`). A build-time ruling: this is code of the same organisation's public repository, copied unchanged but for one import line, and the missing licence is flagged to the operator as a licence-hygiene item.

The vendored `fetchSuppliers` takes no indexer base (it reads `INDEXER_URL` once), so an `indexerUrl` re-points its calls (`src/indexer-fetch.ts`), and a vendored file is not edited. Each result names the agent of an identity-marketplace advert (`agentId`, the row's `agent_id` through the vendored `rowAgentId`; null for a legacy advert). `selectLlmSupplier` is bounded: at most `maxCandidates` (6) suppliers are asked, within `budgetMs` (120 s) from the call, the request in flight being cancelled when the budget runs out. Tested in `test/select-supplier.test.ts`.
- `src/fleet-verify.ts`: `verifyFleetReceipt`, the check of a fleet sub-receipt before an Accept, and the types `FleetVerifyInput` and `FleetVerification`. The vendored `verifyReceipt` compares `response_hash` with the sha256 of the result text, and a fleet supplier hashes a canonical envelope (`src/commitments.ts`), so the hash the buyer recomputes is an input. Five of the eight rows are the vendored `verifyReceipt`'s own, called and not copied: `supplier_key_matches`, `signature_valid`, `on_chain_hash_matches`, `prompt_hash_matches` and `fields_match`, the agent_did check of Part 2 section 6.3 (exactly the 8 receipt fields for a legacy escrow; those 8 and `agent_did` = `did:vector:<agent_id>` for an identity-marketplace escrow, whose `agent_id` is an input). Three are written here: `escrow_ref_matches` (both refs through the vendored `canonicalRef`), `response_hash_matches` (against the recomputed hash) and `model_matches`. The verdict is `VERIFIED` only when all eight pass, `FAILED` when one fails, and `INCOMPLETE` when none fails and the hash on chain was null. The verifier never throws on a malformed receipt, one nested too deeply for the vendored `canonicalize` to walk included: the vendored call has no guard for that in its on-chain row (a supplier can send such a receipt within the poll's size cap), so it runs inside a `try` and its five rows fail on a throw, the on-chain row being skipped only when there was no hash to compare. Only the error of the on-chain callback propagates (it is awaited first and not caught), and a callback result that is neither a string nor null fails the on-chain row. Tested in `test/fleet-verify.test.ts` and, with the vendored call replaced by one that throws, in `test/fleet-verify-throw.test.ts`.
- `src/index.ts`: the public surface.

The tests: `test/vendored.test.ts` (this manifest, both ways, and the public surface), `test/signing.test.ts`, `test/deployment.test.ts`, `test/commitments.test.ts` (the values the plan pins, the prompt hash the fleet pins in its own tests, and the fields each hash covers), `test/config-and-fixtures.test.ts` (the mainnet defaults, the vendored fixtures driving `planPostEscrow`, `resolveEscrowLineage` and `lucidForAddress`, the identity fixtures driving `identityDeploymentFrom`, `planPostEscrow`, `resolveEscrowLineage` and `readEscrowOutput` in the identity layout, and `module1Consent` over the reward accounts of the identity world), `test/provider-reward-account.test.ts` (the vitest port of the source's `packages/shared/test/provider-reward-account.test.ts` at `94bd293`: `OgmiosProvider.getRewardAccount` over a stubbed fetch), `test/fleet-build.test.ts`, `test/real-chain.test.ts`, `test/fake-chain.test.ts`, `test/guards.test.ts`, `test/fleet-verify.test.ts` (real Ed25519 signatures from keys generated per job, and the fleet commitments as the hashes), `test/fleet-verify-throw.test.ts` (the vendored `verifyReceipt` replaced by a stand-in that throws, and the arguments it is handed), `test/fleet-clients.test.ts` and `test/select-supplier.test.ts`. `test/advert-koios.ts` is a fake Koios for the advert a Post reads, shaped after the one of the mcp-server's `marketplace-build.test.ts`; it is not a copy, so it sits outside `test/fixtures/`. `test/fake-fetch.ts` is the fake fetch of the last two (it answers by method and URL and records the calls); it is not a copy either. ## Re-vendoring

1. Take the new pin (a commit of Apex-Fusion/mcp-server).
2. Re-vendor `packages/vector-read` first, at the same pin: its `src/datum.ts` and `src/identity-codec.ts` are the datum codecs and the identity codecs that the copies here import (see `packages/vector-read/VENDORED-FROM.md`).
3. For each row, take the blob at the pin with `git cat-file blob` (never a working file of a CRLF checkout), cut the excerpts again after checking that the line ranges still hold the same code (`build.ts`: `lucidForAddress` and `toBuildResult`; `tx.ts`: the header and the `blake2b` import, `lovelaceToAda`, `cborUint`, `cborBytes` and `deriveNftAssetName`), and apply the import rewrites listed above, one line for one line.
4. If a copy now imports a file that is not here, copy that file whole too and add its row. For the shared `tx.ts`, add the lines that are needed to the excerpt instead, whole lines in source order. A name of the datum module or of `identity-codec.ts` comes from `@vsa/vector-read` or `@vsa/vector-read/identity-codec`. If the mcp-server changes its version of `@lucid-evolution/uplc`, pin the same version in `package.json`.
5. Apply the config.ts deviation again: the source's `config.ts` defaults to testnet, so set the defaults of lines 2-4 to the mainnet values above. A fresh blob brings the testnet defaults back, and `test/config-and-fixtures.test.ts` fails until they are mainnet again.
6. Apply the unit-name deviation again: search every copy under `src/vendored/` for the unit name, in any case, and rewrite each line that names it, one line for one line. The name becomes `units`. An identifier that spells it becomes `units`, after a check that no other `units` is in its scope. List each rewritten line under Rewritten lines. Leave the copies under `test/fixtures/` byte-identical. `scripts/specs.test.mjs` fails on a line that is left.
7. Check the verbatim exceptions above against the new copies (the em dash lines of `fixture-provider.ts`, the unit name of `identity-world.ts`, and any new one), and update their line numbers here.
8. Recompute the sha256 column (`sha256sum`), update the commit column and this file, and run `pnpm --filter @vsa/buyer-core test` and `pnpm typecheck`. `test/vendored.test.ts` fails on a copy without a row, a row without a copy, and a sha256 that no longer matches.
