# Advocate

The strongest one-sided brief for a position, with citations: it argues one side only, by design, omits counter-arguments, and says so in every output. Capability `research.advocate.onesided.v1`.

Status: PROPOSED (built, not deployed). Since 2026-10-13. The service is built and its tests run the search, the pages, the model and the check against stand-ins for the Brave Search API, the result pages, a chat supplier of the marketplace, the chain and OpenRouter, with no network. It has had a registry record since 2026-10-19 and has no advert yet, and no job has run. `specs/advocate.md` at the repository root is the specification; this page and the manifest describe the code.

The service sits behind the template runtime (`vector-agent-template`, `CAPABILITY_KIND=custom`). The runtime holds the supplier key, claims the escrow of the hirer and posts the job to this service as the body of `POST /`. The service reads the request, sends two queries to the Brave Search API, made from the subject and the side, with no language parameter, fetches up to 12 of the result pages itself and reads their text, asks one model for the strongest brief for that side, with a quote of a page for every claim, drops each quote it does not find in the text of its page and each argument left with none, and answers with the brief, which the runtime hashes into the one receipt it signs. It buys the model call first from a chat supplier on the Vector marketplace, through a bonded escrow it posts with a buyer key of its own, verifies the supplier's signed receipt and accepts it, and makes the call through OpenRouter only when that hire fails. The service holds the buyer key and no other chain key. It holds two API keys of third parties, `BRAVE_SEARCH_API_KEY` and `OPENROUTER_API_KEY`. An escrow that a job leaves behind is settled later by a janitor.

`agent.json.template` is the manifest with placeholders. The service renders the real manifest from its environment when it starts and serves those bytes at `GET /agent.json`. It never serves the template itself. `<OPERATOR_CONTACT>`, `<AGENT_DID>`, `<SUPPLIER_PKH>`, `<SUPPLIER_PUB_KEY_HEX>` and `<ADVOCATE_BUYER_PKH>` in the template stand for the values in the table below.

## Run it

The service needs Node 22 or later, a buyer key, a key of the Brave Search API and a key of OpenRouter. It needs no other program and no model of its own. A run locks real value: a job posts an escrow on Vector mainnet from the buyer key. Put on that key only what you mean to commit to escrows and fees. On a machine with the repository:

```bash
pnpm install
cd agents/advocate
export ADVOCATE_BUYER_PRIV_KEY_HEX="$(cat /path/to/buyer-key.hex)"    # read from a file: a key typed on a command line stays in the shell's history
export SERVICE_AUTH_HEADER="Bearer $(openssl rand -hex 32)"           # the token a caller must send, generated by openssl
read -rs BRAVE_SEARCH_API_KEY && export BRAVE_SEARCH_API_KEY           # paste the key of the Brave Search API; it is not shown
read -rs OPENROUTER_API_KEY && export OPENROUTER_API_KEY               # paste the key of OpenRouter; it is not shown
export SUPPLIER_PUB_KEY_HEX=$(openssl rand -hex 32)                    # a public key for a run on this machine, never one that holds anything
export SUPPLIER_PKH=$(node --import tsx --input-type=module -e "import { blake2b224Hex } from '@vsa/vector-read'; console.log(blake2b224Hex(process.env.SUPPLIER_PUB_KEY_HEX))")
mkdir -p /tmp/advocate-state                                           # where the record of the escrows it posts is kept
OPERATOR_CONTACT=ops@example.test ADVOCATE_STATE_DIR=/tmp/advocate-state PORT=9094 pnpm start
```

The service logs the buyer address it derived from the key; that is the address that receives the collateral and the float.

`SUPPLIER_PKH` and `SUPPLIER_PUB_KEY_HEX` must be the key hash and the public key of one key pair, or the service does not start: on the host, step 4 of `deploy/host/RUNBOOK-advocate.md` makes the pair with `gen-keypair`; for a run on a machine of your own, the two `export` lines above make a public key and its blake2b-224, which is all the service checks of the supplier key, since it never signs with it.

It stops at start, with the variable named, when `OPERATOR_CONTACT`, `ADVOCATE_BUYER_PRIV_KEY_HEX`, `SUPPLIER_PKH`, `SUPPLIER_PUB_KEY_HEX`, `SERVICE_AUTH_HEADER`, `BRAVE_SEARCH_API_KEY` or `OPENROUTER_API_KEY` is not set, when a setting is not well formed, when `SUPPLIER_PUB_KEY_HEX` is not the public key of `SUPPLIER_PKH`, when `ADVOCATE_BUYER_PKH`, `ADVOCATE_BUYER_ADDRESS` or `ADVOCATE_BUYER_PUB_KEY_HEX` is not the key's, when the buyer key is the key of `SUPPLIER_PKH`, when `ADVERT_MAX_PROCESSING_MS` is below 8 min, or when it cannot write to its state directory. It calls neither the Brave Search API nor OpenRouter at start: the first job is the first use of the two keys.

A secret in the wrong line of an env file is the mistake the start guards against. The buyer key is looked for in every other setting the service reads, in its raw and its bech32 form, before any check can print that line, and found there it stops the start, naming the variable and not showing the value (a value that is published, such as `AGENT_DID`, would otherwise go out in `/agent.json`). The service token is looked for in every other setting the service reads, whole or by its credential (the part after `Bearer `), each when it is 16 characters or more, and found there it stops the start, naming the variable and not showing the token. Each of the two API keys is looked for in every other setting the same way. So none of the four is in a message, a log line or an answer, and the manifest is searched for all four once more before the service listens. No message of the service shows a setting that is hex-shaped or long, only its length, and a line of the log about a key that a third party refused gives its HTTP status and never the key. `SUPPLIER_PUB_KEY_HEX` must be the public key of `SUPPLIER_PKH`, which catches a private key put in its line.

## Routes

| Route | Answer |
|---|---|
| `GET /healthz` | `{"ok":true}` while the service runs: it has no check of its own beyond answering |
| `GET /agent.json` | the manifest, the bytes `JSON.stringify` gives |
| `POST /` | the wire message and nothing else, with the `authorization` header of the runtime. Without it, 401 `{"error":"unauthorized"}` |
| any other route | 404 `{"error":"not_found"}` |

`GET /healthz` and `GET /agent.json` are matched on their path, whatever the query string, and a `HEAD` of either gets the headers of the `GET`, its `content-length` included, and no body.

The body of `POST /` is the wire message: a one-element array whose `content` is the request JSON as a string, and whose `role` is `user`. It is read up to 1000000 bytes. The request JSON is `{ "subject": "...", "side": "for", "audience": "...", "length": "standard", "language": "en" }`, with `subject` and `side` required; the manifest publishes its schema under `interface.request_schema`, and what a schema cannot say under `interface.notes`. The answer to a job is `JSON.stringify(result)`, serialised once, exactly the bytes the runtime hashes.

`POST /` requires the `authorization` header to be exactly the value of `SERVICE_AUTH_HEADER`, the value the template runtime sends with every call to a custom service. The runtime and the service read it from the same env file, and neither blanks it. A call without the header, or with another value, gets 401 `{"error":"unauthorized"}`, with no detail, before the body is read and before the job slot is taken. The two values are compared in constant time (`crypto.timingSafeEqual` on their sha256 digests), and a refusal is logged once a minute at most, with a count and nothing the caller sent. `GET /healthz` and `GET /agent.json` need no header: the image's health check sends none, and the manifest is public.

One job runs at a time, because the escrow of its chat sub-job comes from the one buyer wallet. A second job that arrives while one runs gets 409 `{"error":"busy"}` and nothing is started. A job whose caller hangs up, as the runtime does when its own budget for the job runs out, is stopped: its fetches and its call to OpenRouter are aborted, nothing of the job is kept, and the slot is free for the next one; a hire of a chat supplier that has begun first ends on its own terms, its escrow accepted or recorded for the janitor. A job has its own deadline, 300000 ms after its request arrives, 60 s inside the runtime's `SERVICE_TIMEOUT_MS` of 360000. The search gets at most 15000 ms of it, for two queries one after the other, each at most 10000 ms; the fetch of the pages ends 45000 ms after it begins, or 20000 ms before the deadline when that comes first; the hire of a chat supplier ends 95000 ms before the deadline; the call through OpenRouter, when that hire fails, gets the smaller of 90000 ms and the time the job has left less 5000 ms, and is not made when that comes to under 15000 ms.

While a job runs, the server writes an interim `102 Processing` line every 60 s to a client that speaks HTTP/1.1, ahead of the answer, which is the same 200 with the same body as it would be without them. The reason is that the runtime's fetch gives up after 300 s of silence (the headers timeout of undici, behind fetch), and a job of this service can take its whole deadline of 300 s, and longer when a hire is in its Accept: without the lines the runtime would report `service_unreachable` at the five minute mark. The lines stop when the job ends.

## Errors

A refusal is `{"error": "<code>", "message": "<words>"}` with the status in the table. A job that fails at a third party, in the hire or in the check (the 502 row), or with `store_write_failed` (500), gets a fixed message, `The service could not do this job (<code>). The operator's log has the detail.`, because the runtime copies the first 200 characters of a failure to the buyer and the detail is the operator's: the whole message is in the log. A job cut at its deadline (`deadline`, 422) keeps its words, which are about the time the job had and hold nothing of the request. `aborted` (499) is the answer to a caller that has hung up, which nobody reads. `shutting_down` says in words that the service is stopping. Anything else is 500 `{"error":"internal"}` with no detail; the cause is in the log, by message only. The 401 has no message at all.

| Status | Codes |
|---|---|
| 400, the message | `bad_wire` (not the one-element message array), `request_too_large` (over 1000000 bytes) |
| 400, the request | `bad_shape` (a request JSON that does not parse, or one that breaks a rule of the request) |
| 401, the caller | `unauthorized` (the call has no authorization header, or one that is not the token of the service) |
| 422, the job | `deadline` (the job ran out of its time, or too little of it was left to call the model) |
| 499, the caller hung up | `aborted` (the job was stopped when its caller hung up; nobody reads this answer, and the log keeps its code and the time the job took, not its words) |
| 502, a third party or the check | `search_failed` (both queries failed, or the Brave Search API refused the key), `search_empty` (no usable result), `no_sources` (no page kept), `inference_failed` (the answer of the chat supplier was verified and the Accept of its escrow could not land), `model_failed` (the call to OpenRouter failed), `model_output_invalid` (the answer is not the JSON of a brief), `no_supported_claims` (the check dropped every argument) |
| 503, the service cannot take a job now | `shutting_down` (the service is stopping) |
| 500, the service | `store_write_failed` (an escrow was posted and could not be recorded), and `internal` |

No refusal locks anything of the service's before the Post of its chat sub-job, and a job that fails after that Post leaves its escrow to the janitor. The runtime fails the job, and the hirer reclaims the escrow after its `deliver_by`. The 400s and the 401 come before anything is searched or fetched.

## The search, the pages and the model

The search makes two queries to the Brave Search API, one after the other, the second at least 1100 ms after the first, since a plan of the Brave Search API may take about one query a second: the subject alone, and the subject followed by the words of the side (`arguments in favour` for `for`, `arguments against` for `against`, the position itself otherwise), each cut at a word boundary to at most 400 characters and 50 words, 10 results each. The queries are made from the subject and the side, with no language parameter and no country. A query that answers 429 is asked once more, 1100 ms later. The language of the request is not sent: it is the language the model is asked to write the brief in. The results of the second query come first; a result is kept once, by its scheme, host and path, and only with an https URL; at most 12 are kept.

Each result page is fetched by the service, four at a time, through the same safe fetch as the MCP server's (https only, no redirect followed, private and reserved addresses refused), at most 1048576 bytes and 15000 ms a page, with the user agent `vector-service-agents/advocate (+https://github.com/Apex-Fusion/vector-service-agents)`. A page is kept when it answers 200 with HTML or plain text and its text, its tags and scripts taken out, has at least 200 characters; its first 12000 characters are what the model reads and what the check searches.

The model is asked with a fixed prompt that asks for the strongest brief for the side, with no counter-argument, no rebuttal and no concession, a thesis and 3 arguments for `short` or 5 to 7 for `standard`, every claim citing the numbered pages, each with a quote of 20 to 300 characters copied from that page. The call is bought first from a chat supplier on the Vector marketplace: the service chooses an Active `llm.text.generate.v1` advert of a model on `LLM_MODEL_ALLOWLIST` priced at most `LLM_MAX_PRICE_LOVELACE`, checks that the buyer wallet covers its escrow, posts the escrow with the buyer key, sends the prompt as one input string with no temperature, no JSON mode and no token limit, polls, runs the seven checks of the sub-receipt, accepts the escrow, and only then reads the answer as a brief. When that hire fails, the call is one chat completion through OpenRouter, `OPENROUTER_MODEL`, `deepseek/deepseek-v4-flash` unless the setting names another, with `temperature` 0, a JSON answer, at most 2000 tokens for `short` and 4500 for `standard`. The rule of the fallback is the table under How it buys in `specs/advocate.md`. The check can leave fewer arguments than were asked for, and a job that keeps none fails. The result names the model `<model> via the Vector marketplace` or `<model> via OpenRouter`, and the path under `inference`; the receipt names `advocate-v1`.

## The check

A cited quote is kept when its number names a page the service kept, and the quote, normalised (Unicode NFKC, lower case, the left single quote U+2018 and the apostrophes U+2019 and U+02BC made U+0027, the double quotes U+201C and U+201D made U+0022, the dashes U+2013 and U+2014 made U+002D, whitespace collapsed), is 20 to 300 characters long and is found in the normalised excerpt of that page. The result gives a kept quote in the words of its page: the part of the excerpt it was found in, with the case, the marks and the characters of the page, whatever form the model wrote it in. A quote that fails is dropped, an argument left with no quote is dropped, and the thesis stays. A job whose every argument is dropped fails with `no_supported_claims` (502). An argument lists a page and a quote once, however often the model cites them in it. The sources of the result are the surviving ones, once for each page and quote, in the order they are first cited. Every result carries `declared_bias`, with the side as the intake keeps it (`for` and `against` in lower case, a position as given) and the statement `This brief argues one side only, by design, and omits counter-arguments.`, and `omitted_by_design`, `counter-arguments and rebuttals`.

## The buyer wallet, the state and the janitor

Before it posts anything a job reads the buyer wallet, within 10000 ms: a pure output of at least 5000000 lovelace kept as collateral, and a float outside it that covers the lock of the escrow at the price of the advert chosen and the fee of a Post and of an Accept, 500000 lovelace each. A job that the float cannot cover locks nothing and gets its brief from OpenRouter. On the marketplace path a job costs the buyer wallet about 2.2 at today's fleet price of 0.2: the price and the supplier bond of 1, which the chat supplier receives on Accept, and about 1 in fees; the buyer bond of the sub-job comes back.

Every escrow a job posts is written to `stranded.json` in `ADVOCATE_STATE_DIR` (default `/data`, a volume in the image) the moment its Post is confirmed, and removed once its Accept is confirmed. The janitor starts with the service and looks at the file every minute: from 5 s after an escrow's `deliver_by` it reclaims an Open or Claimed escrow, and it keeps a Submitted one that its supplier may release. It makes no transaction while a job runs. A file that is not a list stops the start and is left as it is, because starting without it would forget escrows that still hold a lock. The file holds the bookkeeping of the escrows (references, times, the hop, a transaction hash), never a request, a page or a brief. A write of the file that fails after a Post fails the job with `store_write_failed` (500), and the service posts no escrow again until it restarts: every later job gets its brief from OpenRouter, with `inference.fallback_from` `marketplace_off`.

## Stopping

On SIGTERM (`docker stop` sends it) or SIGINT the service takes no new job and no new connection, stops its janitor, and waits up to 300 s for the job that is running to end, its Accept included. The wait is on the job itself: it ends when the job has its answer, or when the job has been stopped because its caller hung up. A job ends within 300 s of its arrival, and a hire in its Accept at that time runs on, so the wait is that long at most in practice but for that tail. A pass of the janitor still in flight after 30 s is abandoned, with a log line. A job that ends in time is answered, if its caller is still there, and the service exits 0. One still running after 300 s is abandoned: its connection is closed, the log names the escrows the state directory holds for the janitor of the next start, and the service exits 1. The container is killed when its grace period ends, so `stop_grace_period` in the compose file is 330 s: the 300 s of the wait and 30 s more, for the log line and the exit code of a job the service had to abandon. A second signal ends the process at once.

## Manifest

`agent.json.template` is the JSON that `manifestFromEnv` prints with the five placeholders. A test keeps the two equal, byte for byte, so change the template by changing `manifestFromEnv` and regenerating it: `pnpm --filter @vsa/advocate template`.

| Variable | Use | Default |
|---|---|---|
| `OPERATOR_CONTACT` | `operator.contact` | none. Required: the service stops at start without it |
| `ADVOCATE_BUYER_PRIV_KEY_HEX` | the buyer key, 64 lowercase hex characters, which posts and settles the escrow of the chat sub-job. Never published, never logged | none. Required: the service stops at start without it |
| `SUPPLIER_PKH` | `identity.controller_pkh` and `keys.supplier_pkh`, 56 hex characters | none. Required |
| `SERVICE_AUTH_HEADER` | the `authorization` header the runtime sends with every call, which `POST /` requires: `Bearer ` and 64 hex characters, made with `openssl rand -hex 32`. Never published, never logged | none. Required: the service stops at start without it |
| `SUPPLIER_PUB_KEY_HEX` | `keys.pub_key_hex`, 64 hex characters, the public key of `SUPPLIER_PKH`: the service stops at start unless its key hash is `SUPPLIER_PKH` | none. Required: the service stops at start without it |
| `BRAVE_SEARCH_API_KEY` | the key of the Brave Search API, sent as `X-Subscription-Token` with each of the two queries. Never published, never logged | none. Required: the service stops at start without it |
| `OPENROUTER_API_KEY` | the key of OpenRouter, sent as `Authorization: Bearer <key>` with the call to the model. Never published, never logged | none. Required: the service stops at start without it |
| `OPENROUTER_MODEL` | the model the service asks through OpenRouter, as `<provider>/<name>`; the fifth gap of the manifest names it, and so does the `model` of a result on the OpenRouter path | `deepseek/deepseek-v4-flash` |
| `ADVOCATE_BUYER_PUB_KEY_HEX` | optional. The public key of the buyer key, as step 4 of the runbook writes it; a value here that is not the key's stops the service at start | derived |
| `ADVOCATE_BUYER_PKH` | optional. `keys.buyer_pkh` is always the key hash derived from the buyer key; a value here that is not that hash stops the service at start | derived |
| `ADVOCATE_BUYER_ADDRESS` | optional, as above, for the mainnet enterprise address of the buyer key, which the log names at start | derived |
| `ADVOCATE_STATE_DIR` | where `stranded.json` is kept | `/data` |
| `LLM_MODEL_ALLOWLIST` | the chat models the service may hire on the Vector marketplace, comma separated, in order of preference; the fifth gap of the manifest names the first, beside the model of `OPENROUTER_MODEL` when the two differ | the model of `OPENROUTER_MODEL` |
| `LLM_MAX_PRICE_LOVELACE` | the most the chat job may be priced at, in lovelace: an advert priced above it is not hired, and when no advert at or under it can be, the job gets its brief from OpenRouter | `1000000` |
| `VECTOR_MARKETPLACE_INDEXER_URL` | the marketplace indexer the chat suppliers are found in | the default of `packages/buyer-core` |
| `AGENT_DID` | `identity.did` | empty |
| `AGENT_VERSION` | `version` | `0.1.0` |
| `ADVERT_PRICE_LOVELACE` | `terms.price_lovelace` | `3000000` |
| `ADVERT_MAX_PROCESSING_MS` | `terms.max_processing_ms`; at least 480000, because the deadline of a job assumes the 8 min window | `480000` |
| `AGENT_STATUS_CHIP` | `status.chip`, in lower case | `proposed` |
| `AGENT_STATUS_SINCE` | `status.since`, as YYYY-MM-DD | `2026-10-13` |
| `ADVERT_EXPLORER_URL` | `links.explorer_advert` | empty |
| `PORT`, `HOST` | where the service listens | `9094`, `0.0.0.0` |

Numbers (and `PORT`) must be non-negative integers. `AGENT_STATUS_CHIP` must be live, deployed or proposed, in any case. A value that breaks a rule stops the service at start, and the error names the variable. The chain endpoints are Vector mainnet's; `VECTOR_OGMIOS_URL`, `VECTOR_KOIOS_URL` and `VECTOR_SUBMIT_URL` change them, and `packages/buyer-core` reads them. The advert `detail_uri` points at `GET /agent.json` and its `detail_hash` is the sha256 of the bytes served there. Adverts are immutable, so a changed manifest means a retired advert and a new one: `OPENROUTER_MODEL` and the first model of `LLM_MODEL_ALLOWLIST` are in it, through the gap that names the model.

## Tests

```bash
pnpm --filter @vsa/advocate test
```

The tests need no network and no key. The Brave Search API, the result pages, the chat supplier and OpenRouter are stand-ins (`test/fake-fetch.ts`, with the answers and the pages of `test/fixtures/`, and the chat supplier and its indexer in `test/fake-chain-support.ts`), the chain is the fake chain of `packages/buyer-core`, and a fake clock runs the budgets of a job. The pages of the fixtures are written by hand, and nothing is downloaded.

## Image

`Dockerfile` builds the service image on `node:22-bookworm-slim`. The build context is the repository root, because the image installs the workspace from the lockfile: `docker build -f agents/advocate/Dockerfile -t vsa/advocate:dev .`. The image runs as the `node` user under `tini`, listens on 9094 and answers `/healthz` for its health check. `/data` is a volume owned by `node`. The image has no Python and no model, and it fetches nothing at run time but what a job asks for, what the hire of a chat supplier reads and sends, and what the janitor asks of the Vector chain about the escrows a job left behind. The memory limit is set where the container is run; the compose file gives it 1024m.
